# Åkerögården — Implementation Plan

**Based on:** requirements.md, erd.md
**Audience:** the developer building v1.
**Purpose:** a dependency-ordered, phased path from empty repo to production launch. Each phase lists its **goal**, **scope & deliverables**, the **requirements it satisfies**, and **exit criteria** (what "done" means before moving on).

---

## How to use this plan

- Phases are **dependency-ordered** — each builds on the one before. Don't start a phase until the prior phase's exit criteria are met.
- Every requirement ID (FR-xx / NFR-xx) traces back to requirements.md. If a phase seems to conflict with the SRS, the **SRS wins** — raise it, don't silently diverge.
- The data model is fixed in requirements.md §8 and visualised in erd.md. **Add EF Core migrations incrementally**, introducing each entity in the phase that first needs it (noted per phase). **Pre-go-live exception — ✅ DONE (2026-07-13).** With no production data to preserve, the accumulated 14-migration per-phase history was wiped and regenerated as a single consolidated baseline, `20260713155158_InitialSchema` (commit `1ddce7d`). Entities added in that window — notably `AuditLog` (§8.15) — landed **in** the baseline rather than as incremental migrations on top of it. **The exception expires when Phase 10c migrates the production database:** from that point production holds real data, every schema change is an incremental migration, and history is never rewritten again.
- **Tombstoned requirements need no work:** FR-12, FR-41, FR-43 (merged/removed), and FR-46 (dropped). They're listed in the SRS only to keep numbering stable.

### Cross-cutting concerns (apply in every phase, not a separate phase)

- **Testing (NFR-26–28):** three tiers — **unit** tests for business logic (pricing tiers, retention/deletion dates, token expiry, meal/participant validation); **integration** tests for every API endpoint against ephemeral containers; and **end-to-end / UI** tests (Playwright for .NET — `Microsoft.Playwright`, introduced in Phase 6) covering key browser journeys, accessibility (axe-core), and responsive reachability at 360/768/1280. **No pixel/visual-regression diffing** — it is flaky across OS/font rendering (local macOS ↔ CI Linux) and high-maintenance; assert behaviour and structure instead. CI fails the build on any test failure. Write tests *with* each feature, not after.
- **Swedish-only UI (NFR-32):** all public and admin text is Swedish from day one. No English strings, no i18n framework.
- **GDPR:** no personnummer (NFR-23); personal data only in EU regions (NFR-06/24); no personal data in URLs (NFR-05).
- **Data integrity:** editing/deactivating reference data must never alter saved bookings (NFR-14); snapshots back this (NFR-15/16/33/34).
- **UI approach — functional first, polish last:** In Phases 1–5, build screens that are functional and readable, not polished. No animations, no pixel-perfect spacing, no mobile optimisation — just enough UI to drive and test the feature. Exception: the Phase 0 design system (tokens, base layout, logo component) is foundational and must be done properly — skipping it means inline styles everywhere and a worse retrofit later. Polish, responsiveness, and visual refinement happen in Phase 6 (UI/UX).

- **Secrets:** SMTP and connection strings as encrypted app settings / Key Vault — never in source.

Each slice = entity + EF Core migration + Interactive Server CRUD screen (create / edit / deactivate / display-order) + its hard-delete guard + unit tests, merged to the phase branch before the next begins. The only intra-phase dependency is **Room → Building**; the remaining entities are independent and ordered simplest-first so the CRUD/soft-delete/guard pattern established in slice 1 is proven before the two slices with novel mechanics (CleaningZone's array bundle, Facility's Blob upload).

### Phase 1 implementation notes

- **Hard-delete guard — unit-tested now, wired to real references later.** Every "block on hard-delete when referenced" rule (FR-16/20/26/30/88) targets entities that do not exist until Phase 3–4: Facility ← `BookingFacilitySelection` (§8.13) and CleaningZone ← `BookingCleaningSelection` (§8.12) arrive in Phase 3; MealOption ← `MealPreference` (§8.6) and Room ← `Participant.RoomId` (§8.5) arrive in Phase 4. Phase 1 implements a per-entity `CanHardDelete` check unit-tested against a stubbed reference-count source; the real reference counts are wired in as those tables land. **Building's guard is two-layered:** in Phase 1 it blocks deleting a building that still has rooms; the booking-transitive check (FR-16, "room assignments on any booking", via Room → `Participant.RoomId`) is added in Phase 4. Deactivation (soft) is fully implemented and tested in Phase 1.
- **CleaningZone bundle scope (slice 4).** `IncludesZoneIds` is a PostgreSQL `uuid[]` column (Npgsql), not a foreign key — so there is no DB constraint and validation lives in the app layer. Phase 1 stores the array and validates in the admin CRUD that included IDs reference existing active zones and that a bundle does not include another bundle. The mutual-exclusion *checkbox behaviour* on the inquiry form is a Phase 3 concern (it lives on the public form), not Phase 1.
- **No computed totals on CRUD screens (C8).** `AmountExVat` and `VatRate` on PriceRule and CleaningZone are stored and displayed exactly as entered. The admin edit screens must not render any derived "total incl. VAT" figure — that would violate the no-monetary-totals rule.

**Exit criteria:** a guest completes a booking end-to-end from the email link; token single-use/expiry/regeneration all behave; snapshots are stored; room conflicts are detected; admin can correct details post-submission; unit tests cover token expiry and meal/participant validation, integration test covers the completion submission.

### Render mode — Static SSR + progressive JS (consistent with the public Static-SSR rule)

The completion form stays **Static SSR + progressive-enhancement JS**, like the Phase-3 public forms — *not* an Interactive Server circuit. This was reconsidered deliberately (a token-gated Interactive Server island was weighed and rejected), with the decision resting on three axes:

- **Security surface:** Static SSR is the simpler thing to reason about on a public endpoint — every interaction is a stateless HTTP POST that re-carries and re-validates the token; no server-held circuit state, no unauthenticated interactive principal, and the existing Redis IP rate limiter applies directly. (The `/_blazor` SignalR endpoint already exists app-wide for the admin panel, so an interactive public page would not newly expose it — but it *would* newly have anonymous, token-only principals running server-side interactive components, which Static SSR avoids.)
- **Performance (this workload):** completion is low-volume and fill-once, so server capacity is a non-issue either way; what the guest actually feels is in-form responsiveness on a possibly-rural/mobile connection. Static SSR runs the toggles/meal-matrix/"same for all days" **client-side with zero latency** and degrades gracefully (a post works or you retry); an Interactive Server circuit round-trips every trivial UI update to the server and a dropped circuit interrupts the whole session (risk of lost input). Static SSR performs better on the axis that matters here.
- **Cost:** Interactive Server's only real advantage was avoiding hand-rolled nested binding + JS. That risk is bounded by the design constraints below, so it does not outweigh the security/performance edge of Static SSR.

**Implementation-risk controls (these are the plan, not a hope) — they turn the "variable nested collection" fear into a fixed-cardinality, server-authoritative form:**

1. **Overnight rows are fully server-pre-rendered**, count = the booking's `OvernightGuestCount` (known at render). There is *no* client-side add/remove for overnight participants, so the participant/meal indices are fixed and known when the HTML is generated — the nested `participant × day × meal` grid is a fixed-size structure with deterministic field names, not a variable-length collection assembled on the client.
2. **The per-day meal grid is rendered server-side** from `MealsByDayCalculator` (the stay dates are known), so which day/meal `<select>`s exist is decided on the server, not built in JS.
3. **Day guests use server round-trip add/remove** via named submit buttons on the SSR `EditForm` (Blazor SSR's supported multi-button postback re-renders the bound model with one more/fewer row) — *not* client-side row cloning. Each day-guest row is a **flat** record (single `AttendanceDate` + breakfast + optional lunch/dinner + dietary), so even added rows involve no nested client binding.
4. **JS is confined to pure presentation** that also works with JS disabled: the `IsFullBoard` show/hide, the "same for all days" convenience fill, and the day-guest section visibility. The **server handler is authoritative** — it re-derives (drops meal data for self-catering, drops day guests for `SelfCateringAll`, ignores meals on non-applicable days) regardless of client input, exactly the Phase-3 `InquiryNormalizer` pattern.
5. **Reuse the proven Phase-3 mechanics:** public `MainLayout` already disables Blazor enhanced-nav (`data-enhance-nav="false"`); no explicit `<AntiforgeryToken/>` (Phase-0 400 bug); and every SSR form is **curl-POST + real-browser smoke-tested** before a slice is called done (the Phase-3 lesson — construct-in-memory tests miss form-binding nulls and JS-timing bugs).

Token handling is unchanged by the render mode: `/slutfor/{token}` validates the token server-side on GET (invalid / expired / used / non-`Approved` → static Swedish error), and the submit handler re-validates token + booking status inside the state transition before committing.

### Scope boundary — Phase 4 ends at `DetailsComplete`

Phase 4 stops when the guest submits and the booking reaches `DetailsComplete`. The admin transitions `DetailsComplete → Active` ("mark arrived") and `Active → Completed` ("mark finished"), and the **thank-you email on `Completed`**, are **Phase 5** work (the §2.5 state machine already permits both transitions; only the admin UI actions and the email are deferred). Phase 4's Satisfies row is therefore exactly FR-48/49/54–62 · NFR-15/16/18/33/34 — no `Active`/`Completed` behaviour.

### Build order — six vertical slices (Phase 4)

Like Phases 1 and 3, Phase 4 is built as independently reviewable vertical slices, each merged to the phase branch (with its unit **and** integration tests) before the next begins. The ordering is dependency-driven: the data foundation, pure meals-by-day logic, and the long-deferred hard-delete guards come first; the token page + render-mode decision are proven early (slice 2) before the form is built on top; overnight-participant capture + submit is the core (slice 3); day guests reuse that machinery (slice 4); room assignment with its live exclusions + conflict detection is a self-contained concern (slice 5); and admin post-submission edit comes **last** (slice 6) because it depends on all participant data existing. ### Scheduled-job mechanism — in-process `BackgroundService` + Always On (NOT app-only deploy)

The daily automation (14-day reminders, 30-day pre-deletion warnings, GDPR deletion) runs from a single in-process hosted **`BackgroundService`** (`DailyJobRunner`) — no new Azure resource. It ticks once per day (computes the delay to the next configured run hour in **Europe/Stockholm**, sleeps, runs), and on each tick it opens a **fresh DI scope per run** (the booking/email services are scoped) and runs each job in turn; a job that throws is logged and never aborts the others (NFR-13 style). Each job is **idempotent** — guarded by a persisted sent-marker (`DeletionWarningEmailSentAt` for the warning, a new `ReminderEmailSentAt` for the reminder) so a restart or double-run cannot double-send or double-delete.

On App Service **B1 the app is unloaded after ~20 min idle**, which would stop the `BackgroundService` and skip runs. Reliable daily execution therefore requires **`alwaysOn: true`** in `main.bicep`'s `siteConfig`. Always On is free and does not change the flat B1 price (the server is billed whether awake or idle). Because this is an infra/config change and the pipeline deploys only app code, **Phase 5 is not an app-only deploy** (like Phase 3's Redis): the Always On setting must be applied to staging by hand (`az webapp config set --always-on true`, or a `main.bicep` redeploy) **before the phase branch merges**, and reconciled into prod at Phase 10c. B1 is single-instance, so no distributed-lock/leader-election is needed.

### List downloads — libraries & delivery

Participant and food-preference lists are generated **on demand from an admin button** and **streamed directly** as a file download (in-memory, not persisted to Blob) — the lists are ≤300 rows, always reflect current snapshot data, and persisting copies would only add cleanup and stale-copy risk. **PDF** via **QuestPDF** (Community license — free for orgs under the revenue threshold; set `QuestPDF.Settings.License = LicenseType.Community` at startup), **Excel (`.xlsx`)** via **ClosedXML** (MIT). Both build off the **snapshot** fields (`MealPreference.MealOptionSnapshot`, `Participant.RoomAssignmentSnapshot`, dietary, attendance date) so a list reflects what was agreed even if reference data changed since (NFR-15/16).

### Design approach (this phase is run as UX/product design, not page styling)

## Phase 10b — Public/Admin surface separation ✅ COMPLETE (merged to main 2026-07-17)

**Goal:** make FR-70 ("the admin panel shall be … fully separated from the public site") **true**, structurally, for the first time. Today one web app serves every route on both hostnames; after this phase the public and admin surfaces are two independent applications that share only data and design. Sequenced deliberately **before** 10c so production is *born* separated, never retrofitted.

**Depends on:** Phase 10a complete (two real subdomains bound — the condition that made the gap observable). **Blocks:** Phase 10c — production must not be provisioned until the target topology is settled.

**Decision — reverses the direction logged in 10a.** The 10a follow-up recorded a 3-project code split with **Option 1** (both hostnames on one App Service, framework-native host gating) chosen and **Option 2** (two App Services on the same B1 plan) parked. Reassessed here as a day-one architecture question with no deadline pressure: **Option 2 is chosen; Option 1 is rejected.** The 3-project code split stands — it is the load-bearing part. What changes is the topology.

- **Why Option 2 is the real solution.** Separation becomes a property of the assembly graph *and the deployment* — there is no host-discriminating code anywhere to drift or maintain. It is genuine **process isolation** (the internet-facing public process never loads Identity, SignalR, or admin code — a vuln in one surface's stack cannot reach the other), which is the strongest honest reading of "fully separated." `/admin` on the public host becomes a genuine 404 (the code isn't in the process), not an `[Authorize]` redirect.
- **Why Option 1 was rejected.** It satisfies the *letter* of FR-70 while keeping the public process loaded with the entire admin + Identity + SignalR stack, and every single-process mechanism re-introduces a runtime host-discriminator somewhere. It was chosen in 10a only to avoid a second deploy target — a constraint that doesn't survive day-one scrutiny for two security-differentiated surfaces.
- **Cost:** zero. The App Service **Plan** is the billing unit; two sites on one B1 plan, plus a second managed SSL cert, are free. The only real trade-off is two .NET processes sharing one B1 instance's 1.75 GB RAM — comfortable for this traffic profile (2–3 admins, low booking volume), and **not a one-way door** (moving admin to its own small plan later is trivial).

**Design rationale / rejected approaches (migrated from the 10a follow-up — do not re-litigate):**

- **Rejected: host-sniffing middleware.** Two hand-maintained path lists (admin route prefixes + a "shared infra" static-asset exclusion list) in `Program.cs`. A workaround: it re-encodes routing knowledge that already lives in `@page` directives as a parallel lookup table that silently drifts. Root cause of the ugliness: Blazor discovers routable pages by scanning an *assembly*; while public and admin share one assembly, **any** guard degenerates into a runtime classifier. Reverted; branch `phase_10a_host_separation` deleted.
- **Verified framework caveat (why single-app gating is a dead end).** Two `MapRazorComponents<T>()` roots in one app, each with `RequireHost(...)`, **throws `AmbiguousMatchException`** — both roots try to serve `/_framework/*` (dotnet/aspnetcore#52216, #52631; no shipped first-class API as of .NET 10). The single-app alternatives (`MapWhen` sub-pipelines, or one host-scoped `Router`) carry unverified sharp edges (`MapStaticAssets` per branch — #62249; render-mode endpoint inside a branch). **The two-app topology sidesteps all of this**: each app has its own single root component and its own `/_framework`, so none of these caveats apply.

**The split (compiler-enforced surface membership):**

- `AkeroGarden.Web.Core` — Razor Class Library. `DbContext`, entities, services, booking engine, email, audit, `site.css` + self-hosted fonts, shared layout fragments/design primitives.
- `AkeroGarden.Web.Public` — references Core. **Pure Static SSR** (+ progressive JS). No Identity, no Interactive Server, no SignalR, no admin assemblies. Owns: public pages, inquiry/booking creation, availability, the magic-link completion form (token-auth, not Identity), Redis rate limiting, guest-facing emails. Bound to the public host.
- `AkeroGarden.Web.Admin` — references Core. **Interactive Server + ASP.NET Core Identity.** Owns: admin pages, login/logout, list downloads, invite lifecycle, the `DailyJobRunner` background service (runs in exactly one process), admin-side audit actor. Bound to the admin host.

The split also forces a cleaner allocation of concerns that co-location was hiding: **Redis → Public only** (only the inquiry form is rate-limited), **background jobs → Admin only** (keeps the internet-facing process purely request-serving), **each app owns its own Data-Protection key ring** (public: antiforgery on the booking form; admin: the auth cookie — different payloads, shared nothing).

## Phase 10c — Production pre-stage (DNS-independent) ✅ COMPLETE (2026-07-21)

**Goal:** stand production up completely — provisioned, deployed, populated and verified — while `akerogarden.se` still serves WordPress. Production runs on its Azure default `*.azurewebsites.net` hostnames throughout this phase; nothing here is visible to the public or reversible-under-pressure.

**Depends on:** Phases 10a and 10b complete — production reuses the same client-tenant access and Bicep pattern proved on staging, and must be provisioned against the **two-app topology** settled in 10b so it is born separated.

> **Why 10c and 10d are split (do not recombine).** Almost everything go-live needs — provisioning, config reconciliation, SMTP and deliverability proof, the restore drill — has no dependency on where the domain's DNS points. Only hostname binding, managed-SSL issuance and the WordPress retirement genuinely require the switch, because Azure cannot issue a managed certificate until the domain already resolves to the App Service. Keeping them fused would put slow, discovery-heavy work (quota lead times, a spam-placement fix) inside the one window where the public site is half-migrated. The split moves that infrastructure work into 10c, so 10d is short and scripted. **The one deliberate exception is the jurist review of the legal text:** it is DNS-independent and could sit in 10c, but the client chose to run it immediately before launch (decision 2026-07-20), so it lives in 10d as the launch's long pole — provisioning was decoupled from it precisely so 10c's engineering need not wait.

**Scope & deliverables:**

The work is sequenced into seven steps. The ordering principle: everything free-and-slow with external latency (App Service quota) runs first, then provisioning and verification proceed on their own schedule, and the environment is powered down once verified. **The jurist review of the legal text is deliberately *not* a 10c dependency** — it is postponed to just before go-live and gates **10d** (decision 2026-07-20; the legal text is DNS-independent but was moved to 10d for scheduling, decoupling it from 10c so provisioning need not wait on it). 10c's own cost is bounded by powering the environment down after Step 4.

### Step 0 — Free items with external lead time (start immediately)

Nothing here provisions anything or costs anything, and each has a turnaround measured in days.

- **Region / quota decision — do this first.** `prod.parameters.json` sets `location: swedencentral`; staging was forced there because North Europe had 0 App Service quota. **Verify Sweden Central actually has B1 quota in the client's subscription** — the parameter file is an assumption until checked. If it doesn't, a quota request is a support ticket with a turnaround measured in days, not minutes.
- **`asuid` domain-verification TXT records staged at one.com.** Add the `asuid.akerogarden.se` / `asuid.admin` `TXT` records now. These prove domain ownership to Azure and **carry no traffic whatsoever** — the live WordPress site is completely unaffected. Pre-staging them means the ownership check is already satisfied when 10d flips the traffic records, so certificate issuance starts immediately instead of waiting on TXT propagation inside the cutover window.

### Step 1 — Make `prod.parameters.json` deployable (desk work, no cost)

As committed, the prod parameter file **cannot deploy**. Three fixes:

- **Add `seedAdminEmail` + `seedAdminPassword`.** Both are required params in `main.bicep` with no defaults, and neither is present in `prod.parameters.json` — the deploy fails at parameter validation before doing anything. The password is a secret, so it follows the same CLI-passed pattern as the other three placeholders.
- **Empty the hostname arrays** — `publicHostnames: []`, `adminHostnames: []`. Throughout 10c the apex still resolves to WordPress, so binding the real hostnames fails; this is exactly what staging hit in Phase 10b Slice 4. The real hostnames go in as part of 10d, where they become true. Leaving them in the file now makes the IaC assert something false about the current state.
- **Point `publicBaseUrl` / `adminBaseUrl` at the `*.azurewebsites.net` hostnames** for the duration of 10c, flipped to the real domains in 10d. This is a config value, not a code change — and it is the source of the magic-link caveat noted under Step 4.

Also **decide the production backup posture here** (e.g. `geoRedundantBackup: Enabled` for DR), because it is set at PostgreSQL server creation and cannot be changed afterwards without rebuilding the server.

### Step 2 — Provision (the cost clock starts here)

Provisioning is decoupled from the jurist review (decision 2026-07-20) — it proceeds on its own schedule and does not wait for the legal text. Be aware of the cost trade this creates: B1, PostgreSQL and Managed Redis bill from provisioning, and Redis plus provisioned Postgres storage keep costing even when the apps are stopped, so production may accrue that cost for the weeks between 10c verification and the 10d cutover. Step 6's power-down bounds it; the environment is not billed for compute while stopped, only for Redis and storage.

- **Create the resource group, then validate the template as the first action** — `az group create` for `akerogarden-prod`, then `az deployment group validate` (or `--what-if`) with `main.bicep` + `prod.parameters.json` and the CLI-passed secrets, *before* the real `create`. This is the earliest point ARM validation can run: `validate` requires an existing resource group, so it cannot be done in Step 1 while `akerogarden-prod` does not yet exist. (The `prod.parameters.json` structure itself is already proven — the az CLI reads only the `parameters` object from the file, so the root `_comment` key is discarded and never reaches ARM; and staging deploys this same template cleanly. What `validate`/`what-if` still catches here is anything environment-specific: SKU/quota availability in the region, the two-app resource loop, and the Key Vault access policies.)
- Run `main.bicep` with `prod.parameters.json` to create the production resources (App Service B1, PostgreSQL Flexible Server VNet-only, Blob Storage, Redis, Key Vault) in the client's subscription/tenant.
- **Pass all four secrets on the CLI** — `postgresAdminPassword`, `smtpUsername`, `smtpPassword`, `seedAdminPassword`. The parameter file holds `REPLACE_VIA_CI_SECRET` placeholders; omitting any one of them resets the Postgres admin password and overwrites the Key Vault SMTP secrets. **This same hazard recurs at 10d's drift re-apply** — it is not a one-time precaution.
- Add a role assignment for `akerogarden-devops-deploy` scoped to the new `akerogarden-prod` resource group (the Azure DevOps service connection and `Deploy - Production` pipeline already exist from Phase 10a — no new pipeline wiring needed).
- **Configure the manual-approval check on the `production` Environment** in Azure DevOps. Still unconfigured since Phase 10a, and it must exist *before* the first real production pipeline run.
- Validate VNet isolation (`publicNetworkAccess: Disabled` on PostgreSQL).

### Step 3 — First production deploy + reconcile hand-applied config

- **First production deploy** through the existing `Deploy - Production` pipeline, targeting the default `*.azurewebsites.net` hostnames. *(The final deploy against the real domains is 10d.)*
- **Reconcile into prod** the infra/config that was applied by hand to staging across earlier phases, and confirm it actually arrived via Bicep rather than being assumed: Always On (Phase 5), `ForwardedHeaders` + DataProtection Blob/KV key persistence (Phase 7).
- **Watch for the stale Key Vault reference cache.** An App Service restart does *not* refresh Key Vault references — only an app-setting change or the 24-hour expiry does. If production SMTP misbehaves on first boot, this is the first suspect, not the credential values; it cost a full debugging session on staging. See `infra/ops/operations.md`.

Grouped deliberately: these all need the apps running, so they are done together and the environment is powered down immediately afterwards.

Reconcile the prod SMTP port/TLS mode with what staging proved (staging uses 465/SslOnConnect; the prod param currently defaults to 587). *(This is also where the **exhaustive §9 email-template render check** deferred from Phase 7 is completed — see the Phase 7 Email note.)* **This works without the DNS switch** because SMTP authentication and the sending domain's SPF/DKIM/DMARC are entirely independent of where the *website's* `A` record points — so the whole email surface is provable before cutover. **One caveat carried into 10d:** links inside emails (the `/slutfor/{token}` magic link especially) are built from `publicBaseUrl`/`adminBaseUrl`, which read `*.azurewebsites.net` during this phase. Correct for testing, but one magic-link email must be re-verified in 10d after those settings flip to the real domains.
  - **Email deliverability / spam placement (raised at the Phase 8 demo, 2026-07-09).** At the client demo the inquiry/approval emails sent from **staging** landed in the recipient's **spam** folder. Almost certainly a **staging-only artifact**: staging sends from a temp One.com mailbox (`temp@amaeli.se`, port 465) whose domain lacks aligned SPF/DKIM/DMARC, whereas **production sends from the `akerogarden.se` domain whose SPF/DKIM/DMARC are already configured and are explicitly preserved by the one.com cutover above** — so prod should authenticate and deliver to inbox. **Action here:** as part of the prod-SMTP E2E, confirm the sending domain's SPF/DKIM/DMARC are valid and aligned, send a real test to an external inbox (Gmail/Outlook), and check headers/placement land in inbox (not spam). Fix DNS auth on the **sending domain** only if it fails — **never touch one.com's live email records outside this controlled step.** *(Diagnosis captured now; the real verification/fix belongs to production SMTP + DNS, hence Phase 10c.)*
- **Occasional UI lag — verify warm (raised at the Phase 8 client demo, 2026-07-09).** Intermittent lag noticed on staging is most likely a **B1 idle-power-down cold-start artifact** (staging is powered down when idle; public-page perf already measured PASS warm in Phase 7 — NFR-08: 0.12–0.23 s). Confirm whether it reproduces on a **warm production-sized instance** as part of the prod-perf verification below; if it only appears after idle, no code change is needed — if it reproduces warm, it becomes a real bug (candidate causes: circuit reconnection, an unindexed query, cold JIT).
- **Backups + restore drill (NFR-12 / NFR-29 — moved here from Phase 7, decision 2026-07-08):** confirm production PostgreSQL automated backups exist (retention, earliest restore point), then run the **restore drill** — a point-in-time restore to a throwaway server and verification that real data comes back — using `infra/ops/restore-drill-runbook.md`. **On production use the runbook's Path 2 only (in-VNet verification); Path 1's temporary public endpoint is forbidden — it would expose real guest PII.** Decide production backup posture at provisioning (e.g. `geoRedundantBackup: Enabled` for DR). This satisfies the existing "backups proven restorable" exit criterion. **Scope, stated honestly:** run pre-cutover the drill proves the *mechanism* — that automated backups exist, that a point-in-time restore succeeds, and that the reference data comes back intact. It does **not** prove restore-of-guest-PII, because no guest data exists until after launch. That is the correct trade (the mechanism is what can be broken by misconfiguration), but the drill should be recorded as proving the mechanism, not overclaimed as a full production-data restore.
### Step 5 — Populate production

- **First admin account + reference-data entry.** Create the initial production admin, then populate real reference data (physical buildings, buildings, rooms, meal options, facilities, price rules, cleaning zones) through the admin panel on the default hostname. Done here rather than after cutover so the public site is fully populated the instant DNS flips, rather than launching empty and being filled in under time pressure.
- **Entry is manual, and deliberately so.** The obvious-looking alternatives — restoring staging's database into production, or pointing `DemoDataSeeder` at prod — were both considered and rejected (2026-07-20). Staging's database carries synthetic bookings in every lifecycle state, blocks, magic-link tokens and staging's own Identity accounts, none of which belong in production; and `DemoDataSeeder` **wipes every application table before reseeding**, which is a standing footgun against real guest data if the flag is ever left set (see `infra/ops/seeding.md`). Building a separate reference-data-only seed path was weighed and judged not worth it: **the actual dataset is small enough to enter by hand in a sitting**, and manual entry doubles as a real walkthrough of the admin UI on production. Do not re-propose an automated prod seed without a materially larger dataset to justify it.

*(VAT rates, cleaning-zone amounts, and every other reference-data value are the client's to set and edit through the admin panel — not engineering scope, and not tracked here.)*

## Phase 10d — Cutover & launch

**Goal:** flip the domain and go live. Deliberately short and scripted — every item below is fast and rehearsed, because everything slow was completed in 10c.

**Depends on:** Phase 10c complete. In particular, go-live must not be scheduled until the legal text is jurist-signed — that review is the long pole and it gates this phase, not 10c's engineering work.

**Scope & deliverables:**

- **Privacy-policy + booking-terms legal text jurist-reviewed and live (moved from 10c, decision 2026-07-20).** **Drafts exist** at `docs/legal/Integritetspolicy.md` and `docs/legal/Boknings-och-ordningsvillkor.md` (started 2026-07-11 — see `[[project-legal-documents]]`), grounded in the real controller identity (Kaldeiska katolska Mar Narsay Missionen i Södertälje, org.nr 815601-0129, trading as Åkerögården) and the actual retention logic (§2.7/FR-67–91). Both still carry `[ATT BEKRÄFTA]` gaps (no-show/remaining-balance terms, damage liability, force majeure, cookie section, governing law) and **must be reviewed by a Swedish jurist before publish** — a first draft from an AI assistant is not a substitute for legal sign-off, given GDPR/IMY exposure and Swedish consumer-contract law on the cancellation terms. The privacy policy's **cookie ("Kakor") section** absorbs the cookie-consent assessment: no consent banner is required (only strictly-necessary auth/antiforgery cookies are set today, no analytics/tracking), so this is a documentation task, not a gate implementation. **This is the phase's long pole** — deliberately done just before go-live rather than early, and it gates the launch (NFR-20–24). The legal text itself has no DNS dependency; it sits in 10d only because the client chose to run the jurist review immediately before launch.
- **DNS + SSL:** lower DNS TTLs a day ahead, then configure DNS for `akerogarden.se` (apex — `A`; an apex cannot use `CNAME`) and `admin.akerogarden.se` (`CNAME`). The `asuid` `TXT` verification records are already in place from 10c. Bind the custom hostnames and run `ssl.bicep` for the managed certificates. **Expect the ARM multi-hostname `for`-loop Conflict gotcha** that Phase 10a hit — budget for binding one hostname and one SSL binding manually via `az webapp config hostname add` / `az webapp config ssl bind`, and reconcile the end state back to the Bicep declaration (see `infra/azure/README.md` gotchas). *(Staging's own subdomain binding was handled in Phase 10a.)*
- **Base-URL config flip + final production deploy.** Switch `publicBaseUrl` / `adminBaseUrl` to the real domains and redeploy. **Re-verify one magic-link email end-to-end afterwards** — this is the one 10c verification that does not survive the flip (see the 10c SMTP note).
- **Re-apply Bicep and redeploy to close any drift.** Production may have sat provisioned for weeks while the jurist review ran, with Phase 11 work continuing on `main` in the meantime. Cheap to do, and it guarantees the launched build is current.
- **one.com / WordPress cutover:** one.com is the **registrar + DNS host + email provider**, so the cutover is DNS-record surgery inside one.com. **Retire only the WordPress web hosting** — never touch the DNS zone, the domain registration, or the email records (`MX`, `SPF`, `DKIM`, `DMARC`) and mailboxes, because the app sends guest/admin mail through One.com SMTP; breaking those silently kills every email. Make the **apex `akerogarden.se` canonical and 301-redirect `www`→apex**. Point the apex + `admin` records at Azure; keep WordPress powered but unlinked through a short soak; then decommission the WP hosting. The current live site is trivial (a simple info page — a few images + phone/email), so there is no content-parity work and near-zero rollback risk.
- **Go-live checklist** and post-launch smoke test on the real domains.

**Satisfies:** NFR-20–24 (privacy policy — moved from 10c) · the residual go-live NFRs — production reachable, correctly certificated, and serving the real domains.

**Exit criteria:** the privacy policy and booking terms jurist-reviewed, gap-free and live; go-live checklist complete; the WordPress site decommissioned with DNS + email preserved; production reachable over valid managed SSL on `akerogarden.se` and `admin.akerogarden.se`, with `www` redirecting to the apex; a magic-link email verified to carry real-domain links.

> **Migration discipline resumes here.** The moment 10c migrates the production database, the pre-go-live exception described at the top of this plan expires: production holds real data from launch, so every subsequent schema change is an incremental migration and the history is never rewritten again.
